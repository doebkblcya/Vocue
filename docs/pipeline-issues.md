## 已修复

### A1 — 累计文本兜底

**用户看到**：面试记录里出现「很大、很长一团」，两千到四千字。

**原因**：系统音频是一条从面试开始挂到结束的长连接，`result.text` 是这条连接的**累计文本**。原本的取值链是

```js
lastUtterance?.text || response.body.result?.text || response.body.text
```

拿不到分句时就一路退到累计文本，于是整场对话被当成「面试官刚问的一道题」送进模型。

**证据**：28 分钟那场留下三条——12.7 分处 2107 字、15.7 分处 2705 字、25.3 分处 4087 字，开头都是「我我来面试。嗯。哼。嗯……」，最长那条里裹着 69 段更早的发言。

**修法**：只认 `utterances`；拿不到分句就什么都不做。判断逻辑抽成 `interpretServerFrame`（`src/main/asr/doubao-asr.ts`），测试见 `tests/asr-frame.spec.ts`。

### A2 — 1 秒缓冲：两次判停挨得近时前一句被覆盖

**用户看到**：面试官说了一句话，屏幕上毫无反应。没有提词，事后翻记录也找不到，像他从没说过。

**机制**：服务端判停后，程序不立刻使用，而是把文字存进一个变量，再等 1 秒才提问。那个变量一次只装得下一句——1 秒内第二句判停到来，第二句直接覆盖第一句，被覆盖的那句永远不被显示、保存或提问。覆盖发生在**发给 AI 之前**，所以是「连问都没问」。

**这个缓冲是从哪来的**：Bready（`Suge8/Bready`，`src/main/doubao-service.ts:42`）的注释写着

> `FINAL_DEBOUNCE_MS = 1000 // definite: true 后的防抖，防止豆包语义判停太早`

但它跟我们并不是同一条链路。端点相同（`wss://openspeech.bytedance.com/api/v3/sauc/bigmodel_async`），差别在 `X-Api-Resource-Id`（它 `volc.bigasr.sauc.duration`，我们 `volc.seedasr.sauc.duration`）与请求体（它 `result_type: 'single'` 且未开 `enable_nonstream`，我们 `full` 且 `enable_nonstream: true`）。它当初要防的「判停太早」，未必等于我们也会遇到。

**它在我们这里本来就碰不到**：当时 `end_window_size = 1200`，两句不同的话各自都要攒够 1.2 秒静音才会判停，所以两次判停之间至少隔 1.2 秒——比 1 秒的等待窗口长。计时器总在下一句判停之前烧完，格子总来得及清空。

**那为什么还是删了**：这份安全是**参数送上来的，不是设计保证的**。`end_window_size` 官方推荐 `[800,1000]`，一旦为了 A5 调低，1 秒窗口就会长过判停间隔，A2 立刻从不可达变成可达。而这件事后来真的发生了——阈值已经调到 **1000**，判停间隔和当年的 1 秒窗口正好贴在一起。**删掉缓冲让 A2 从「碰不到」变成「不存在」，同时每道题早 1 秒。**

**修法**：删掉 `finalize()` 和它的同步计时器，`handleMessage` 收到 `final` 帧直接 `onFinal`。没有缓存，就没有可被覆盖的格子。

### A6 — 系统提示词没有总量上限

**已做：前端提醒，不做拦截。**

先撤回原来的风险评估。查了 DeepSeek 官方文档：

| | 数值 |
|---|---|
| 上下文长度 | **1M tokens** |
| 输入（缓存命中） | 0.02 元 / 百万 token（空闲时段） |
| 输入（缓存未命中） | 1 元 / 百万 token |

- **撑不爆**：50 万字 ≈ 30~50 万 token，只占 1M 的 30~50%
- **几乎不花钱**：系统提示词是稳定前缀，会命中硬盘缓存。首次约 0.5 元，之后每题约 0.01 元

所以「成本」和「超出上下文」都不是理由。剩下两个真实损害：**第一道题的首字延迟**（缓存还没建立）、**答案质量**（模型要在几十万字里找相关内容）。

**实现**：`ARCHIVE_MATERIAL_WARN_LIMIT = 100_000`（`src/shared/limits.ts`）。档案编辑页在 JD + 简历 + 补充资料**合计**超过 10 万字时显示一条提醒，**不拦截**，超了照样全文发给模型。

- 数字取 10 万：正常用量（JD + 简历 + 几份笔记）在 3 万字上下，10 万约 3 倍
- 放在**档案**层面而不是文档库：文档库是全应用共享一份，总量只有跟某个档案绑定时才有意义

### A8 — 两处去重会静默吃掉重复的发言

**问题**：同一段文本 5 秒内出现第二遍就不记、不问。这个判断写了两遍：

- `doubao-asr.ts`：拦住不发给 AI
- `interview-session.ts` 的 `recordUtterance`：拦住不写进记录

**为什么删**：音频才是事实来源。服务端判停几次就是几句，不替它猜哪句是重复的。而且这是**静默**删除——删错了你永远不知道，屏幕上没有、记录里也没有，跟 A2 是同一种失败。反过来，真出现重复屏幕上当场看得见，事后能修。**用一个响的故障，换掉一个不响的。**

**证据**：库里那场 28 分钟的面试，97 条面试官发言，10 秒内的时间相邻组合 39 对，相似度最高 0.511，超过 0.8 的 **0 对**。没有观察到重复。

**顺带否决了 Bready 的相似度去重**：它的算法不看字序——注释写「基于最长公共子序列」，实现却是字符集合比对。`项目做了什么` 与 `做了什么项目` 算出来是 **1.000**，会被当成重复吞掉。不适合搬过来。

### B1 / B2 — 调用健壮性

- 首字超时 **8 秒**、整体上限 **60 秒**、`max_tokens` **2048**
- `max_tokens` 只挂在流式路径。复盘生成走的非流式路径**不能加**——复盘正文实测 3022 字，套上会被截断

## 待处理

### A5 — 长问题被切成两段，发两次 AI

**用户看到**：面试官问了个长问题，提词出来了，几秒后被新的替换。最后拿到的是针对后半句的回答。

原来拆成两种情况，**情况 2 已排除**，剩下情况 1。

#### 情况 1：面试官停顿了

**这按设计就是这样，不是 bug。**

规则：静音 **1000 毫秒** → 服务端判停 → 发 AI（约 1 秒；A2 移除后本地不再额外等 1 秒）。

停顿只要超过 1 秒，一定会切成两段、发两次 AI。**参数选择问题。**

可疑点：**1 秒可能太短**，面试官想事情的停顿经常超过这个数。但官方推荐值就是 `[800,1000]`，**这已经取到推荐区间的顶了**——再往上就不是「我们自己保守一点」，而是超出官方建议。

**已定**：从 1200 调到 **1000**（2026-09-19）。理由是在官方认可的范围内尽量少切半句，同时每道题省 200ms。缓冲移除后这颗旋钮不再牵动 A2，可以单独调。

**原先的顾虑已解除**：以前不能把 `end_window_size` 调到 1000 以下，因为判停间隔一旦短过 1 秒缓冲，A2 就会出现。缓冲移除后这颗旋钮自由了，可以单纯按「少切半句 vs 更快出字」来取舍。

#### 情况 2：面试官没停顿

**结论：机制上不可能。「确实发生了」这个判断要撤回。**

文档明确：配置了 `end_window_size` 之后，`vad_segment_duration`（语义分句）**失效**，「静音时长超过该值，会直接判停」。

**判停的唯一触发条件就是静音。没有静音，就不会分句。**

所以「没有停顿也被切」按规则不成立。它只能是情况 1——那段停顿确实存在，只是没被察觉（面试官边想边说的停顿最容易忽略）。

**原来为什么会记成「确实发生了」**：当时把库里相邻两条发言的 `start_ms - end_ms` 当成静音长度，看到几条 `0ms` 就断定「两段之间完全没有静音」。**这个推断是错的**——文档只写了 `start_time` / `end_time` 是「分句起始 / 结束时间戳」，没说它含不含静音。如果它本身就是分句边界，相邻两段天然接在一起，间隔恒为 0，读不出任何东西。

**也找过「两段重叠」的痕迹**（如果切出来的两块是重叠窗口重识别的，切口处会有重复字）：97 条面试官发言里，边界处有 ≥3 字公共片段的共 9 组，但其中 8 组是面试官自己重复了词（「Flask」「SQL」「听不到你」），只有 1 组像切口残留。**不构成一个模式。**

### A7 — 语气词被当成问题，答案被立刻清空（优先级最高）

**用户看到**：正盯着答案准备回答，面试官「嗯嗯」一声，答案瞬间消失。等了几秒，新的回答区一片空白。

**两个问题叠加。**

#### 7-1：任何识别结果都被当成「一道题」

程序不判断内容，只要 ASR 吐出一段定稿，就当成「面试官刚刚提出的问题」发给 AI。

**真实数据**：97 段面试官发言里 **13 段**是这种——「嗯」「哦」「嗯嗯」「是吧？」「嗯，你说。」，占 13%。

模型收到 system prompt 说「你会收到面试官刚刚提出的问题，请为候选人生成提词」，user 消息却是「嗯嗯」，自然什么也答不出来。**空白就是这么来的。**

#### 7-2：新问题一到，答案立刻清空

```js
// interview-session.ts，answerQuestion 开头
this.patchState({
  generating: true,
  answer: '',
  answerSummary: '',
  answerDetail: '',
})
```

**没有任何缓冲。** 哪怕新来的是真问题、哪怕旧答案才看了一半，都是瞬间消失。

**完整时序**：

```
你在读答案 → 「嗯嗯」被识别 → 清空 → 问模型「嗯嗯」是什么问题
          → 模型答不出来 → 空白 → 你既没了旧答案，也没有新答案
```

**为什么优先级最高**：每场面试都会发生很多次，而且直接毁掉你正在用的东西。A2/A3 是静默丢数据（少见），A5 是答错，A7 是**当场毁掉你手上的答案**。

**修法方向**（未定）：

1. 过滤明显不是问题的短句（「嗯」「哦」这类）
2. 清空时机改掉——旧答案应该保留到新答案真正开始产出，而不是一收到问题就抹掉

## 已取消

### A4 — 同一句话被两个回调各上报一次

**原判断**：`onFinal` 和 `onSegmentEnd` 都会调用同一段处理逻辑，同一句话可能触发两次 AI 请求，第二次掐掉第一次。

**为什么取消**：系统音频是一条长连接，「最后一包」只会在连接**收尾**时出现，也就是面试快结束的时候。一整场最多触发一两次，而且那时已经不需要答案。**用户从没遇到过，和这个推断一致。**

它真正影响的是**按住说话**模式（那个模式每说完一段就是一次连接结束）。原判断是拿系统音频的数据去推，搞错了场景。

### A3 — 靠前的分句看不到完成标记

**原判断**：代码读分句列表时只取最后一项（`utterances.at(-1)`）。如果服务端在同一帧里既把第一句标成「已定」、又把第二句加进列表，第一句的完成标记就永远看不到，那一句不会被保存、也不会被提问。

**为什么排除**：

1. **这是从代码推出来的，不是从使用里来的。** 没有任何用户观察指向它。
2. **真实记录里找不到。** 把面试官相邻两条发言里「上一条没说完、下一条也从半句开始」的全部挑出来，共 12 组——其中 9 组的上一条本身就是语气词（「嗯」「哦」），接新句很正常；剩下 3 组确实切在句子中间，但**两半都在**，没有一条是「前半段消失」。
3. **机制上也轮不到它。** 上一段判停发生在它说完之后的**那 1000 毫秒静音里**，那时下一段还没生出来，所以它必然还是列表的最后一项。而且我们用的 `bigmodel_async` 文档写着「只有当结果有变化时才会返回新的数据包」——「已定」本身就是一次变化，会单独占一帧。

**唯一的例外**：某一段特别长时，二遍识别可能慢到下一段已经开始，形成竞态。没有观察到。

**保留 `utterances.at(-1)` 不改。** 如果想彻底不依赖服务端发送时机，可以改成「记住已处理到第几项，只处理后面的」——那是一个只增不减的水位线，不会丢东西。但那是去掉一个隐含假设，不是修 bug，暂不做。
