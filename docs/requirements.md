## 0. 背景

Vocue 是一个本地优先的 macOS AI 面试助手,在上一个会话中已经跑通两条核心语音链路:

- **按住说话**:回答窗口中按住按钮或空格录音,松手时客户端发「最后一包」触发服务端结算。
- **系统音频**:通过 `SystemAudioDump` 持续采集会议声音,由服务端 VAD 按静音判停。

本文档记录在这两条链路之上要做的 9 项微调与迭代。

## 1. 先纠正的两个前提

这两条会影响后续所有判断,先写在这里。

### 1.1 上下文长度不是瓶颈,延迟和成本才是

`deepseek-flash`(DeepSeek-V4.1-Flash)的实际规格:

| 项目 | 数值 |
| --- | --- |
| 上下文长度 | **1M tokens** |
| 最大输出 | 384K tokens |
| 思考模式 | 支持,**官方默认为开启 + effort=high** |
| 视觉 | **支持**(注意:`deepseek-v4-pro` 不支持) |
| 价格(输入·缓存命中) | $0.003 / M(闲时)· $0.006 / M(峰值) |
| 价格(输入·缓存未命中) | $0.15 / M(闲时)· $0.3 / M(峰值) |
| 价格(输出) | $0.6 / M(闲时)· $1.2 / M(峰值) |
| 单图 token 上限 | **1024 tokens**(超出会等比缩放到约 1300×1300) |

当前 `prompt-builder.ts` 里 system prompt 的硬上限:

| 内容 | 分析时 | 面试回答时 |
| --- | --- | --- |
| 岗位 JD | 30,000 字符 | 24,000 字符 |
| 简历 | 40,000 字符 | 32,000 字符 |
| 单份补充资料 | 20,000 字符 | 12,000 字符 |
| 补充资料份数上限 | 5(`register.ts:97` 硬编码) | 同左 |

最坏情况合计约 **11.6 万字符 ≈ 8 万 token**,只占 1M 上下文的约 **8%**。

**结论**:

1. 「能塞多少文档」的答案基本是「随便塞」,**不要为了省 token 去砍文档**。
2. 真正要控制的是**首字延迟(TTFT)**,不是容量。
3. 缓存命中与未命中的价格差 **50 倍**。system prompt 在整个面试期间字节不变,能持续命中前缀缓存 —— **因此要保持 system prompt 稳定,不要在里面塞变化的内容**(例如不要把它和对话历史拼在一起)。

### 1.2 「现在每个问题都是独立的」并不成立

`interview-session.ts:344-363` 已经在传历史:

```ts
const messages: ChatMessage[] = [
  { role: 'system', content: this.systemPrompt },
  ...this.history.slice(-8),
  { role: 'user', content: question },
]
```

**已经有 4 轮(8 条 message)上下文了。**

但存在一个语义问题:历史里的 `assistant` 内容是 **AI 给你生成的建议回答**,而不是「面试官真实说过的话」,也不是「你实际说出口的话」。模型会把这些建议当成「候选人确实这么讲过」,追问时可能顺着自己的幻觉往下走。

所以 R6 的工作不是「从 0 加上下文」,而是「**把上下文换成真实发生过的对话**」。这个区别决定了是否需要先做 R3。

## 3. 逐项展开

### R1 · 评估 system prompt 容量与返回速度

**需求原文**:评估模型能接受多少 system prompt;往里面塞多少文档时返回速度会比较慢。

**现状**:
- `prompt-builder.ts` 已对每部分做了字符级截断(见 1.1 表格)。
- `register.ts:97` 的 5 份上限是硬编码任意值,放开只是一行。
- 补充资料的截断参数(12k)比分析时(20k)更保守。

**方案**:不做产品改动,单独写一个压测脚本直接打 DeepSeek API。测试矩阵:

| 档位 | 目标 system prompt 规模 | 说明 |
| --- | --- | --- |
| A | ~2 万 tokens | 接近当前实际值 |
| B | ~5 万 tokens | |
| C | ~15 万 tokens | |
| D | ~50 万 tokens | |
| E | ~100 万 tokens | 接近 1M 上限 |

每一档测两组:
- **冷启动**:改一个字让缓存失效,测首个请求的 TTFT。
- **二次请求**:system prompt 不变,测缓存命中时的 TTFT。

记录:TTFT、总耗时、`usage` 里的 cache hit/miss token 数。

**注意**:网络和服务端负载有波动,建议同一时段连续跑,每档重复 3 次取中位数。

**状态(2026-09-17)**:暂缓,本轮不实现也不运行压测。

**工作量**:小(半天内出数据)。

**待以后确认**:恢复 R1 时再决定压测脚本是否长期保留。

### R2 · 思考模式开关

**需求原文**:在选项设置里给用户一个自定义选项,打开模型的思考模式,也就是调整思考强度。

**实现状态(2026-09-17)**:设置页已提供关闭、低、高、最大四档。默认关闭;开启后发送对应 `reasoning_effort`,并停止发送思考模式下无效的 `temperature`。界面只展示最终回答,不展示模型思维链。

**官方参数**(DeepSeek 文档):

- 开关:`thinking: { type: 'enabled' | 'disabled' }`
- 强度:`reasoning_effort: 'low' | 'high' | 'max'`(官方映射:`minimal`/`low` → low,`medium`/`high`/`xhigh` → high,`max`/`ultra` → max)
- **官方默认是 enabled + high** —— 当前代码显式关闭,这个默认值选得对。

**已知副作用**:

1. 思考模式下 **`temperature` 会被静默忽略**(不报错,但无效)。当前 `deepseek-client.ts:123` 硬编码了 `temperature: 0.45`。
2. `top_p` 在思考模式下有 0.95 下限;非思考模式下固定 1.0 并忽略传入值。
3. 思维链走 `reasoning_content` 字段,与 `content` 同级。**当前 `stream()` 只读 `delta.content`(`deepseek-client.ts:64`),思考内容会被静默丢弃** —— 不报错,但界面上看不到。若要展示思考过程,需要新增解析。
4. 不带 `tools` 参数时,`reasoning_content` 无需回传,也不会拼进上下文。

**核心矛盾**:面试场景要求 2–4 秒内出话(见第 4 节延迟预算),`high` 强度几乎必然超标。

**当前方案**:实时回答允许用户自行选择强度,设置页明确提示高强度会明显增加首字延迟;默认仍为关闭。

**改动点**:`AppSettings`/`PublicSettings` 加字段 → `settings.ts` 读写 → `deepseek-client.ts` 参数化 → `SetupView.tsx` UI。

**工作量**:小。若要展示思考过程,再加一个可折叠区域。

**已确认**:实时可用但默认关闭,由用户承担延迟取舍。

### R3 · 录制整场面试

**需求原文**:面试开始后,边上有个选项,勾选打开后就可以开始录制整场面试,面试官和我的声音都要录进去。

这是**最复杂**的一项,复杂度容易被低估。

**现状与难点**:

1. **两条音源从不同时存在。**
   - 系统音频:主进程采集(`SystemAudioDump`,24k 立体声 PCM)。
   - 麦克风:渲染进程采集(Web Audio worklet,16k 单声道),且**只在按住按钮的 `sending=true` 期间运行**(`microphone.ts:8-36`)。

   要录全场,麦克风必须改成**全程常开**,这与现有「按住说话」的设计直接冲突。

2. **远端音频里通常没有你自己的声音。** 会议软件一般只混远端参与者,不会把你的声音回传。所以不能靠系统音频一路搞定,**必须双轨**。

3. **项目里不存在任何音频编码器**,全是裸 PCM:
   - 1 小时 24k 立体声 16bit ≈ **346 MB**
   - 1 小时 16k 单声道 ≈ **115 MB**

   要么引入 ffmpeg(打包体积 +30~80 MB,还要处理签名与公证),要么先落 WAV 再离线转换。**这是本项目目前没有的新依赖类型。**

4. **性能陷阱**:`microphone.ts:9` 的 `samples` 是 `number[]`,并且 `splice(0, 1600)` 是 O(n) 操作。按住几秒钟无所谓,**改成全程常开会退化成 O(n²)**。必须先换环形缓冲。

**建议方向**:双轨各自落盘(**面试官轨 / 我轨**),**不要混音**。后面做复盘时,双轨 = 天然的说话人分离,省掉 diarization 这一环。

**改动点**:麦克风常开采集 → 环形缓冲 → 双轨落盘 → 编码/转码 → 权限处理 → 磁盘空间管理 → 异常中断恢复。

**工作量**:**大**。

**待确认**:
- 接受引入 ffmpeg 吗?还是先落 WAV 看看体积能不能接受?
- 录音文件放哪(`userData` 下?用户可选目录?)?
- 面试异常中断时,半截录音怎么处理?

### R4 · 录音文件识别(火山引擎)

**需求原文**:把录到的整场面试交给豆包的火山引擎录音文件识别,不需要实时。

**两个版本**:

| | 极速版 | 标准版 |
| --- | --- | --- |
| 时长上限 | ≤ 2 小时 | ≤ 5 小时 |
| 文件大小 | ≤ 100 MB | — |
| 调用方式 | 同步快速返回 | 异步 submit + poll |
| resource id | `volc.bigasr.auc_turbo` | `volc.bigasr.auc` |

**本场景应走标准版**:面试可能超过 2 小时,且双轨文件可能超过 100 MB。

**必须先验证的点**:当前流式 ASR 用的是 `volc.seedasr.sauc.duration` + 新版控制台 `X-Api-Key`(`doubao-asr.ts:23`)。文件识别是**另一套端点 + 另一个 resource id**,**同一个 API Key 能否直接复用需要实测**(大概率可以,但不能假设)。

**另一个要确认的点**:标准版是否支持**说话人分离**。如果支持,配合 R3 的双轨,复盘质量会明显更好。

**改动点**:新增文件识别客户端模块 → 任务提交与轮询 → 结果落库 → 失败重试。

**工作量**:中。

### R5 · 面试复盘生成

**需求原文**:最后生成一大段文本给 AI 来复盘。

**可行性**:可行。有了 1M 上下文,一整场面试的转写稿可以直接塞进去,不需要切片。

**前置依赖**:R3(录音)+ R4(转写)。

**改动点**:
- 新建存储表(`database.ts` 目前只有 `settings` / `preparations` / `preparation_documents` 三张表)。
- 复盘 prompt 模板。
- 复盘页面(主窗口新增入口)。

**注意**:`database.ts` 没有迁移机制(`user_version` 之类的都没有),只有 `CREATE TABLE IF NOT EXISTS`。**新建表没问题**,但以后若要给现有表加字段,需要自己写兼容逻辑。

**工作量**:中。

### R6 · 追问上下文

**需求原文**:现在每个问题都是独立的,面试官把一个问题的追问拆成两问时,模型解决不好。要给它一点上下文,把前几轮对话也塞进去。

**当前决定(2026-09-17)**:暂时恢复原有 Bready 风格,每次请求附带最近 4 轮“面试官问题 + AI 建议回答”。这能保持建议回答前后一致,但 AI 建议并不等于候选人真实口述;等后续能获得真实回答后再替换。

**要定的三件事**:

1. **塞什么?** 继续塞 AI 建议(现状),还是换成真实对话(面试官的真实提问 + 你实际说过的回答)?
   - 选后者需要先有 R3/R4 才能拿到「你实际说了什么」。
   - 折中方案:至少把「面试官的真实提问序列」保留下来(现在 `finalTranscript` 是单值,会被覆盖)。
2. **塞多少轮?** 现在是 8 条 message。轮数越多,TTFT 越高。
3. **超长怎么截断?** 从头砍 / 保留最近 N 轮 + 早期摘要。

**关键成本差异**:system prompt 稳定 → 命中缓存,R1 的那种优化可以摊平;但**历史每轮都在变,历史部分的 token 每轮都要实付**,而且会让 system prompt 之后的所有内容缓存失效。

**当前方案**:固定保留最近 4 轮完整问答,也就是最多 8 条历史 message,再追加当前问题。

**工作量**:中(策略确定后改动不大,难在实验与取舍)。

**已确认**:当前先沿用 4 轮问题 + AI 建议回答,后续再改成真实对话。

### R7 · 一键截屏提问

**需求原文**:面试官出了一道题,AI 可以一键快速获取屏幕内容,把图片发给大模型(支持视觉),返回回答。

**现状**:
- `windows.ts:142` **已经在用** `desktopCapturer.getSources()` 做录屏可见性自检,截图这条路是通的。
- `deepseek-client.ts:82-105` 已有 `recognizeImage`,但它**把 JD 提取的 prompt 写死在里面**,要泛化。
- 好消息:`ChatMessage.content` 已经支持图片数组,`stream()` 能直接吃图,**不需要新写调用路径**。

**成本**:图片会被等比缩放到约 1300×1300,**上限 1024 tokens/张**,成本可以忽略。

**必须处理的坑**:

1. **置顶回答窗口会挡住题目。** 截图前要先隐藏它,或裁掉它所在的区域。
2. **图片只能放在 `user` message**,放 `system`/`assistant` 会返回 400。
3. **`deepseek-v4-pro` 不支持视觉。** 现在只用 `deepseek-flash` 所以没事,但若以后加模型切换,这是个隐患。
4. **多显示器时选哪块屏。**
5. **隐私**:整屏内容会发送到 DeepSeek,界面上应有明确提示。

**改动点**:IPC 通道 → 截图与裁剪 → 组装 user message → 回答窗口按钮 + UI。

**实现状态(2026-09-17)**:回答窗已增加“截屏提问”。每次发送前明确确认隐私影响;截取鼠标所在显示器;截图时临时隐藏主窗口和回答窗;图片只放入 `user` message;截图结束后用 `showInactive()` 恢复窗口,不抢会议软件焦点。

**工作量**:中。

### R8 · 先出要点,再出详细回答

**需求原文**:生成回答时先给几点重点(几点 blunt answer),让面试者扫一眼就知道要点,不用一直盯着屏幕;详细答案也要生成。

**现状**:`prompt-builder.ts` 里已经有「第一段先给出 1 到 3 句可以立即开口说的核心回答」,但**没有独立的展示区**。

**两条路线**:

| | 方案 A · 单次调用 | 方案 B · 双路并发 |
| --- | --- | --- |
| 做法 | prompt 要求先输出要点块再展开,流式天然先到要点 | 一个短请求专出要点,另一个出详细答案 |
| 延迟 | 零额外延迟 | 要点出现更早,但多一次请求 |
| 复杂度 | 低 | 需要处理两路竞态与中断 |
| 建议 | **先做 A**,不够快再上 B | |

**前置阻塞已解决(2026-09-17)**:`systemPrompt` 数据库字段保留兼容,但开始面试时会使用当前模板、本地档案和已保存分析重新组装提示词。修改模板后,新旧档案都会生效,且不会额外调用模型。

**实现状态(2026-09-17)**:采用方案 A。单次流式调用严格输出 `<quick>` 和 `<detail>` 两段,回答窗将要点放在独立高亮区,随后流式展示详细回答,不增加第二次请求。`quick` 固定 2～3 条、总计约 60 字以内;`detail` 默认约 120～180 字且不重复要点,只有复杂技术题放宽到约 250 字。

**工作量**:小~中(A 是 prompt + 渲染分区;B 要动会话层的并发与中断逻辑)。

### R9 · AI 仿真面试

**需求原文**:把 JD 和简历给它,复用面试档案,让 AI 出题、你回答、AI 打分、判断面试效果和需要补强的地方。

**性质**:这不是微调,是**第二个产品形态**。需要:
- 角色反转的状态机(AI 出题 → 你答 → 评分 → 下一题)。当前 `SessionStatus`(`types.ts:72-81`)只描述「听/说」这一种角色。
- 评分 prompt。
- 报告页面。
- 结果存储。

**工作量**:**大**。

**结论**:同意「后话、不急」的判断,排在最后。

## 4. 贯穿全部的一条主线:延迟预算

系统音频模式从**面试官闭嘴**到**界面上出现答案开头**,固定成本是:

| 环节 | 耗时 | 位置 |
| --- | --- | --- |
| 服务端 VAD 静音判停 | ~1200 ms | `SYSTEM_AUDIO_PARAMS.endWindowSize` |
| definite 后等文本落定 | 1000 ms | `SEGMENT_SETTLE_MS`(`doubao-asr.ts:87`) |
| **小计** | **≈ 2200 ms** | |
| DeepSeek 首字延迟 | 变量 | 取决于 system prompt 与历史长度 |

**R2(思考模式)、R6(长上下文)、R7(图片)三个需求都在抢这之后仅剩的一两秒。**
